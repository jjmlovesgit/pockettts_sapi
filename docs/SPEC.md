# Pocket TTS SAPI: pre-implementation specification

Status: **Gate 1 complete; GO to a scoped SAPI proof**, 2026-11-05. Full benchmark and remaining limits are recorded in `docs/MILESTONE_1_BENCHMARK.md`. This specification makes no claim that Pocket TTS will match Paradee-SAPI's footprint or compatibility.

## Product and scope

Provide a Windows x64 SAPI 5 voice engine that apps can enumerate and select, produces speech locally on CPU, and retains Pocket TTS cloning from a user-supplied audio prompt. Package a working offline runtime, model, tokenizer, selected licensed sample voices, and a prompt-management utility. Keep all source, product names, registry IDs, installer paths, and release artifacts separate from Paradee-SAPI. Support English first. Do not train, fine-tune, quantize, or alter weights during feasibility.

The initial app targets are classic SAPI (`SAPI.SpVoice` and `System.Speech`), 64-bit Windows Speech Properties, Edge Read Aloud, and NVDA's 64-bit SAPI 5 driver. Each is an independent compatibility test. OneCore token enumeration can be explored for Edge and Narrator, but a token alone does not prove WinRT, Narrator, UWP, Chrome Reading mode, Discord, or every app will expose the voice. The current engine is x64; 32-bit SAPI clients are outside scope until an x86 DLL is built and tested. Cloud TTS sites and extensions are outside scope unless they explicitly bridge to local Windows speech APIs. Do not claim universal Windows availability or silently change a system default voice. [Paradee-SAPI's proof](https://github.com/jjmlovesgit/paradee-sapi/blob/main/docs/SAPI_PROOF.md) records these distinctions and the role of SAPI word events in Edge highlighting.

## Upstream findings that shape the design

Kyutai released `english_18m_2026-10` (18.2M), `english_7m_2026-10` (6.9M), and `english_2m_2026-10` (1.9M) plus `_refl` reward fine-tuned variants. The 1.9M pair is experimental. The three official [configs](https://github.com/kyutai-labs/pocket-tts/tree/main/pocket_tts/config) point at revision-pinned, **voice-cloning** weights in `kyutai/pocket-tts`, and separately at `pocket-tts-without-voice-cloning` weights. The latter do not satisfy this product's core requirement. The configs specify 24 kHz mono output and a SentencePiece tokenizer. Their parameter counts include the audio decoder, not necessarily the prompt encoder, runtime, dependencies, or voice files.

Kyutai's [article](https://kyutai.org/blog/2026-10-20-pocket-tts-small/) reports, respectively, 9.9×, 12.6×, and 25× real-time generation on **its** one-thread CPU setup. It reports WER 0.85%, 0.90%, and 1.72%; UTMOS 4.339, 4.356, and 3.906; speaker similarity 0.918, 0.914, and 0.910. Reward fine-tuning changes quality figures but not stated speed. These are upstream measurements, not expected Windows results. The 18.2M flagship is reported to match prior quality; the smallest has a material quality drop. The article's architecture uses an audio prompt before text and a codec decoder to produce 24 kHz audio.

Upstream supplies Python with PyTorch and, in [v4.0.1](https://github.com/kyutai-labs/pocket-tts/releases/tag/v4.0.1), an approximately 7.9 MB downloadable **x86_64 Windows CLI archive** implemented in Rust. The archive is only the executable distribution; model weights and other fetched assets must be included in any offline package and measured separately. Upstream documents `export-voice`: converting an audio prompt to a safetensors voice state is relatively slow, while loading the exported state is fast. The official Rust CLI supports the same generate/export-voice commands and local configs, but its sampling noise can differ from Python. Benchmark both paths where practical; choose a runtime only after checking size, resources, quality, cloning, and a feasible SAPI integration interface. Sources: [README](https://github.com/kyutai-labs/pocket-tts), [release](https://github.com/kyutai-labs/pocket-tts/releases/tag/v4.0.1).

## Voice and cloning contract

SAPI voice tokens are stable identifiers for **a model + a voice state**, not model copies. One shared runtime/model should serve multiple tokens per host when safe. A small starter set of bundled, redistributable sample voices may receive tokens after their individual [voice licenses](https://huggingface.co/kyutai/tts-voices) and generated-state redistribution rights are checked. Each token must actually produce its named voice; a registry alias alone is insufficient.

Each SAPI token keeps the model-specific exported voice state plus three local prompt WAVs used for slow, normal, and fast rate bands. Voice Manager derives slow and fast prompts from the authorized PCM WAV recording and registers all paths on the SAPI/OneCore token. SAPI rates −10…−3 select slow, −2…+2 normal, and +3…+10 fast; this is a three-step pace map, not continuous speed control. The slow and fast WAVs also receive cached `.safetensors` states, which the adapter prefers for low-latency speech; older voices fall back to WAV prompts. The current rate-enabled import accepts 16-bit PCM WAV with one or two channels, sampled from 8 to 96 kHz; MP3 and compressed WAV are not supported by the pace converter. Token registration/removal requests elevation; prompt files remain in the creating user's profile. A missing or invalid prompt/state must fail clearly, without silently speaking as another person. Do not auto-download prompts at playback. The utility must make the upstream model's prohibited-use conditions visible and require lawful authorization for the recorded voice; it cannot prove consent by itself.

## Candidate architecture, selected for Gate 2

- Gate 1 candidate: official `english_7m_refl_2026-10` (6.9M) in the v4.0.1 Rust runtime, with a roughly 5–6 second user-provided prompt or a selected licensed bundled voice. The user approved its short-prompt output. In a one-cycle persistent Rust server run, peak RSS was 251.8 MiB, idle RSS 83.3 MiB, and warm post-speech RSS 149.2 MiB; two local request first-chunk times were 23 and 32 ms. The 18.2M ReFL peak reached 341 MiB in the same setup. Continue comparing Rust library in-process integration and a persistent worker with bounded IPC; select the reliable SAPI host model in Gate 2. Do not use a per-utterance CLI launch without a separate latency/memory justification.
- Implement `ISpTTSEngine`/`ISpObjectWithToken` as a Windows COM engine, with classic SAPI token registration. Explore OneCore registration only with actual Edge tests. Pin model/runtime versions and verify installed file hashes. Installation is self-contained and uninstallation removes only this product's files and tokens.
- Accept SAPI text fragments, normalize text while retaining a mapping to the original UTF-16 offsets, stream or chunk bounded audio to the SAPI site, honor rate/volume where feasible, and respond promptly to stop/purge. Emit sentence and word boundary events with source offsets and audio offsets. Pocket TTS does not document word timestamps; estimated timings may be necessary and must pass Edge highlighting tests before a highlighting claim.
- Defer a user-facing rate/volume/pitch tuning panel. SAPI's host rate control selects one of three cloned-prompt pace variants; it does not change pitch in the adapter's output audio. Changing speaker identity or perceived pitch still requires a different authorized recording and voice token. SAPI volume remains an adapter behavior.
- Validate long text, punctuation, dates/numbers, Unicode, malformed input, multiple simultaneous hosts, and model/voice switching. Errors must reach the host without crashing it. No network request occurs during speech or prompt import once assets are installed; inspect process traffic and file writes to verify.

## Assumptions and risks

| Assumption or risk | Check and consequence |
| --- | --- |
| Small parameter count means small deployment | Measure weights, encoder, tokenizer, binary, licenses, runtime libraries, and cache; the total may exceed the size goal. |
| Official Windows CLI is suitable for SAPI | Measure cold/warm cost and inspect native integration. An out-of-process worker may cost memory and add failure modes. |
| Cloning is preserved in all chosen models | Test the **gated cloning weights** with two lawful audio prompts per model; reject a path that needs the no-cloning repository. |
| Quality metrics transfer to Windows reading | Blind listening and intelligibility checks must cover names, numbers, punctuation, long passages, and assistive navigation. The 1.9M model is experimental. |
| SAPI discovery implies app support | Prove each target app's picker and playback on clean Windows. WinRT and arbitrary apps remain outside initial acceptance. |
| Boundary events yield usable highlighting | User confirms Edge Read Aloud word highlighting works in the current 6.9M installation. Continue checking source offsets for normalized text and repeat on a clean profile; upstream exposes no documented word timestamps. |
| Bundled sample voices may be redistributed | Audit each voice's own license and attribution before bundling; omit any voice with unclear rights. |
| User voice states remain private | Test where source recordings/states are stored, deletion, access permissions, and unintended logs or network traffic. |

## Gates and acceptance

**Gate 0 — source and legal check (current):** pin upstream source/release/model revisions; verify model access terms and each candidate sample voice's license. This document satisfies the design baseline, not legal clearance for a package.

**Gate 1 — local model benchmark (complete; GO):** all three official cloning models were tested. The user approved the Sloane prompt outputs for the three base small models, two reward-fine-tuned small models, and the ~100M reference, including 5.36- and 9.15-second prompt excerpts. A single-model 6.9M ReFL offline payload is projected well below 300 MB, and its persistent Rust server peak RSS was 251.8 MiB in one measured run. Proceed to a scoped SAPI proof with 6.9M ReFL. Repeat memory tests and validate text, prompt, offline, and host behavior before product acceptance.

**Gate 2 — SAPI proof (local proof passed; installed-app acceptance open):** direct classic SAPI enumeration/playback, cancellation, volume, text fragmentation and silence, bounded input, worker restart, boundary events, and rate selection passed on the 6.9M ReFL proof build. The current slow/normal/fast duration ratios were 1.29/1.00/0.82. Cached rate-specific states avoided re-encoding prompts on every utterance. Warm first-audio p95 was below 100 ms in the latest three-band rapid test, and no capture exceeded the calibrated one-second substantial-tail guard in 20 trials per band. `System.Speech` produces a complete non-silent WAV after fixing a host-specific `pcbWritten` behavior. A cold-start bug in the adapter's closed-port health check was fixed: direct cold Elle speech improved from 4,589 ms to 170–172 ms in three development-DLL runs. The user reports the installed fix removed many Edge delays; repeat formal cold Edge and NVDA acceptance before closing the broader Windows-app gate. See [Windows app compatibility](WINDOWS_APP_COMPATIBILITY.md), [latency benchmark](SAPI_LATENCY_BENCHMARK.md), and [rate benchmark](SAPI_RATE_BENCHMARK.md).

**Latency status (2026-11-09):** `src/sapi/pocket_sapi.cpp` buffers the full `/tts` WAV response in `FetchWav` before its first SAPI write; output chunking is not incremental synthesis. Warm SAPI-site first-audio p95 with uploaded prompt WAV variants was 282–286 ms for short inputs. Rapid purge/restart p95 was 525.7 ms; two of 20 captures exceeded the matching baseline's 250 ms stale-tail threshold. These serialized output captures are not proof against simultaneous playback overlap. See [SAPI_LATENCY_BENCHMARK.md](SAPI_LATENCY_BENCHMARK.md). Earlier HTTP chunk measurements do not exercise the rate-aware SAPI request path.

**Warm endpoint diagnostic (2026-11-09):** with the installed 6.9M ReFL server already resident (`english_7m_refl_2026-10`, Butter default voice), 10 loopback `/tts` requests per input gave first 4096-byte HTTP read medians of 36.8 ms (`Z`), 36.4 ms (`a`), 34.4 ms (`yes`), and 35.3 ms (`next`). Full WAV response medians were 70.1, 67.0, 72.2, and 74.3 ms respectively; all returned HTTP 200. This is a useful warm model/server signal, but is **not** the measured SAPI-site first-write time and does not exercise purge/restart races. The dedicated SAPI boundary and rapid-manipulation run remains required before Gate 2 closes.

**Gate 3 — offline package and voice utility (in progress):** the private x64 installer packages only the selected official 6.9M ReFL model. The 1.9M installer choice was removed because custom voice states are model-specific and migration was not validated. The package includes the default Alba prompt pace variants and cached states, the small SoundTouch tempo DLL, its LGPL 2.1 license and source archive, the SAPI engine, and Voice Manager. Voice Manager accepts PCM WAV prompts for three pace variants and keeps the exported state; MP3 and compressed WAV are currently unavailable in this flow. Profile-local prompts remain registered machine-wide, so multi-user visibility/access still needs a design. Repeat clean upgrade, install/uninstall, network-disconnected use, and model redistribution review before a public release.

**Gate 4 — app acceptance (in progress):** Edge Read Aloud picker, playback, and word highlighting passed on the current installation; classic SAPI, standard rate before an utterance, and .NET `System.Speech` passed on the latest proof DLL. NVDA 2026.3.1 now demonstrates custom and language voice selection with its SAPI WASAPI option disabled; the enabled path falls back to Alba on this machine. NVDA navigation latency and interruption, Narrator, clean-profile use, and clean network-disconnected playback remain untested. The x86 SAPI path is out of scope in this build. UWP/AppContainer behavior is exploratory; cloud TTS sites and extensions are outside scope unless they explicitly bridge to local Windows speech APIs. Mid-utterance rate changes remain unverified. See [Windows app compatibility](WINDOWS_APP_COMPATIBILITY.md). Repeat app tests on a clean Windows profile and latest installed build, inspect speech-path traffic, record process resources, and check uninstall/reinstall before describing an app as supported. Other app support needs its own test evidence.
